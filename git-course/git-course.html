Chapter 0

What is version control?

The problem Git solves, what Git and GitHub are, and where Git came from.

The problem

You write a report. You want to keep the old version before a big change, so you copy it. A week later your folder looks like the left side of the picture below, and nobody knows which file is the real one.

What version control does

Version control saves a snapshot of your whole folder each time you ask, with a short note, so you can see or go back to any earlier one.

Think of save points in a game. You play, you save, you play on. If things go wrong, you load an old save. Each save point in Git is called a commit.

It lets youIn plain words
Go backBring back the file exactly as it was last Tuesday.
See what changedLine by line: what was added, what was removed.
Know who and whyEvery snapshot has a name, a time and a note.
Try ideas safelyWork on a copy of the line of work (a branch), and throw it away if it fails.
Work togetherMany people change the same project without overwriting each other.

Git and GitHub are not the same thing

Git is a program on your laptop that takes and keeps the snapshots. GitHub is a website that keeps a copy of your snapshots online so you can back them up and share them.

GitGitHub
What it isA program you installA website (github.com)
Where it runsYour laptopOn the internet
Works offline?YesNo
Needs the other?No. Git works alone.Yes. It stores Git repositories.
AnalogyA cameraAn online photo album

Where Git came from

From 2002 the Linux project used a paid tool called BitKeeper for free. In 2005 that free deal ended, so the Linux developers, and in particular Linus Torvalds (who created Linux), built their own tool. That tool is Git.

They wanted it to be fast, simple in design, good at many parallel branches, fully distributed (every copy has the full history), and able to handle a project as big as Linux.

Git's very first commit was made by Linus Torvalds on 7 April 2005, with the note Initial revision of "git", the information manager from hell.

Source: Pro Git 1.2: A short history of Git · Git's first commit, on GitHub

Install and set up Git

Open a terminal

Git is used by typing commands. On a Mac press Cmd + Space, type Terminal and press Enter. On Windows, install Git from git-scm.com and open Git Bash.

In this book a line that starts with $ is a command you type. Do not type the $. The lines under it are what Git prints back.

Rule 1Check Git is installed with git --version

This prints the version of Git on your laptop. If you see a version, Git is ready.

✓ Works
$ git --version
git version 2.52.0
✗ Breaks
$ git --versoin
unknown option: --versoin
usage: git [-v | --version] [-h | --help] [-C <path>] [-c <name>=<value>]
           [--exec-path[=<path>]] [--html-path] [--man-path] [--info-path]
           [-p | --paginate | -P | --no-pager] [--no-replace-objects] [--no-lazy-fetch]
           [--no-optional-locks] [--no-advice] [--bare] [--git-dir=<path>]
           [--work-tree=<path>] [--namespace=<name>] [--config-env=<name>=<envvar>]
           <command> [<args>]

Why: Git only knows its own spellings. A typo in an option makes Git print unknown option and a list of the options it does accept. If instead your terminal says command not found, Git is not installed: get it from git-scm.com/downloads.

Source: git-scm.com: downloads

Rule 2Tell Git your name

Every commit records who made it. git config --global user.name sets the name. --global means “for every repo on this laptop”.

✓ Works
$ git config --global user.name "Asha Rao"
$ git config --global user.name
Asha Rao
✗ Breaks
$ git config --global user.name

Why: With a value, the command saves it. Without a value, it reads it back. On a fresh laptop nothing is saved yet, so reading prints nothing and Git ends with an error code (1). It looks like nothing happened; that silence is the answer “not set”.

Rule 3Put a name with a space inside quotes

The terminal splits what you type at spaces. Quotes keep Asha Rao together as one value.

✓ Works
$ git config --global user.name "Asha Rao"
$ git config --global user.name
Asha Rao
! Trap: no error, wrong result
$ git config --global user.name Asha Rao
$ git config --global user.name
Asha

No error, but Git saved only Asha. The word Rao went to Git as a separate extra argument, not as part of the name.

Rule 4Tell Git your email

The email is also stored in every commit. Use the same email as your GitHub account, so GitHub can link your commits to you.

✓ Works

Rule 5Name the first branch main

A new repo starts with one branch. Today Git calls it master unless you choose a name, and prints a long hint every time. GitHub and most teams use main.

No commits yet

nothing to commit (create/copy files and use "git add" to track)

hint: call:

Rule 6See everything you set with --list

Your global settings live in one plain text file in your home folder: ~/.gitconfig.

✓ Works
$ git config --global user.name "Asha Rao"
$ git config --global user.email asha@example.com
$ git config --global --list
user.name=Asha Rao
user.email=asha@example.com
$ cat ~/.gitconfig
[user]
	name = Asha Rao
	email = asha@example.com

Why: --list shows each setting as section.key=value. The file shows the same settings grouped under [user]. You can edit that file by hand, but the command is safer.

A repository is a watched folder

A repository is a normal folder that Git watches, plus a hidden .git folder where Git keeps every snapshot. Your files stay where they are. Git only adds the .git folder.

Rule 1Git commands only work inside a repo

Most Git commands look for a .git folder in the current folder or one above it. git init creates it.

✓ Works
$ git init
Initialized empty Git repository in /Users/you/git-practice/.git/
$ git status
On branch main

No commits yet

nothing to commit (create/copy files and use "git add" to track)
✗ Breaks
$ git status
fatal: not a git repository (or any of the parent directories): .git

Why: Before git init there is no .git folder, so Git has nothing to read and stops with fatal. After it, git status works and says there are no commits yet.

Rule 2git init adds a hidden .git folder

Run git init once per project, inside the project folder. ls -a lists hidden files too.

✓ Works
$ git init
Initialized empty Git repository in /Users/you/git-practice/.git/
$ ls -a
.
..
.git
! Trap: no error, wrong result
$ git init -q
$ echo hi > notes.txt
$ git add notes.txt
$ git commit -q -m "Add notes"
$ rm -rf .git
$ git log
fatal: not a git repository (or any of the parent directories): .git

Deleting .git gives no warning, and every snapshot is gone. Your current files stay, but the history does not. Never delete .git.

Why: . and .. mean “this folder” and “the folder above”. The only thing git init added is .git.

Rule 3A new file is untracked until you add it

echo "text" > file creates a file with that text in it. Git sees the new file but does not save it yet.

✓ Works
$ git init -q
$ echo "Buy milk" > notes.txt
$ git status
On branch main

No commits yet

Untracked files:
  (use "git add <file>..." to include in what will be committed)
	notes.txt

nothing added to commit but untracked files present (use "git add" to track)

Why: Git never saves a file you did not ask it to. Untracked means “Git sees it, but has never saved it”. That stops junk files from slipping into your history.

Rule 4git add puts a file in the staging area

Staging means “I want this in my next snapshot”.

✓ Works
$ git init -q
$ echo "Buy milk" > notes.txt
$ git add notes.txt
$ git status
On branch main

No commits yet

Changes to be committed:
  (use "git rm --cached <file>..." to unstage)
	new file:   notes.txt
✗ Breaks
$ git init -q
$ git add note.txt
fatal: pathspec 'note.txt' did not match any files

Why: Git now lists the file under Changes to be committed. In the second box the name is misspelt (note.txt); Git cannot find that file, so it stops with pathspec ... did not match any files and stages nothing.

Rule 5git commit -m saves the snapshot

-m is the message: a short note saying what you changed. Each commit gets an ID.

✓ Works
$ git init -q
$ echo "Buy milk" > notes.txt
$ git add notes.txt
$ git commit -m "Add shopping notes"
[main (root-commit) d5b8600] Add shopping notes
 1 file changed, 1 insertion(+)
 create mode 100644 notes.txt
✗ Breaks
$ git init -q
$ echo "Buy milk" > notes.txt
$ git commit -m "Add shopping notes"
On branch main

Initial commit

Untracked files:
  (use "git add <file>..." to include in what will be committed)
	notes.txt

nothing added to commit but untracked files present (use "git add" to track)

Why: root-commit means it is the first one. 1 file changed, 1 insertion(+) says one line was added. In the second box nothing was staged, so the commit is refused: the staging area is empty.

Rule 6git log shows the history

Newest first. --oneline shows one line per commit with a short ID.

✓ Works
$ git init -q
$ echo "Buy milk" > notes.txt
$ git add notes.txt
$ git commit -q -m "Add shopping notes"
$ echo "Buy eggs" >> notes.txt
$ git add notes.txt
$ git commit -q -m "Add eggs"
$ git log
commit 51198a5714354ef2b065ed9b467b544059eee247
Author: Asha Rao <asha@example.com>
Date:   Mon Oct 26 10:00:10 2026 +0530

    Add eggs

commit d5b86009571f89f120e52f74bdc0422b694d4ad3
Author: Asha Rao <asha@example.com>
Date:   Mon Oct 26 10:00:07 2026 +0530

    Add shopping notes
$ git log --oneline
51198a5 Add eggs
d5b8600 Add shopping notes
✗ Breaks
$ git init -q
$ git log
fatal: your current branch 'main' does not have any commits yet

Why: Each commit shows its full ID, the author, the date and the message. >> adds a line to the end of a file (one > would replace it). A repo with no commits has no history to show, so git log stops with an error.

The loop you will repeat all day

1. Edit files. 2. git status to see what changed. 3. git add the changes you want. 4. git commit -m. Back to 1.

Rule 1A changed file must be added again

After you edit a file that is already saved, Git marks it modified. There is no git update: you use git add again.

Start: a repo with notes.txt committed.

✓ Works
$ git init -q
$ echo "Buy milk" > notes.txt
$ git add notes.txt
$ git commit -q -m "Add notes"
$ echo "Buy eggs" >> notes.txt
$ git status
On branch main
Changes not staged for commit:
  (use "git add <file>..." to update what will be committed)
  (use "git restore <file>..." to discard changes in working directory)
	modified:   notes.txt

no changes added to commit (use "git add" and/or "git commit -a")
$ git add notes.txt
$ git commit -m "Add eggs"
[main 6b8e176] Add eggs
 1 file changed, 1 insertion(+)

Why: git add means “put this file's current content in the tray”, not “start tracking”. That is why it is the same command for new and changed files. It lets you pick which changes go into each snapshot.

Rule 2Stage several files at once

List them, or use . which means “everything in this folder”.

✓ Works
$ git init -q
$ echo a > a.txt
$ echo b > b.txt
$ echo c > c.txt
$ git add a.txt b.txt
$ git status --short
A  a.txt
A  b.txt
?? c.txt
$ git add .
$ git status --short
A  a.txt
A  b.txt
A  c.txt
! Trap: no error, wrong result
$ git init -q
$ echo menu > menu.txt
$ echo 'my password' > secret.txt
$ git add .
$ git status --short
A  menu.txt
A  secret.txt

git add . took secret.txt too. No error. Always run git status before committing. Chapter 6 shows how to make Git ignore such files.

Why: A means added to the staging area. ?? means untracked. --short prints one line per file instead of the long form.

Rule 3A commit saves only what is staged

Rule 1git restore file throws away an unstaged edit

It copies the file back from the last saved version.

Start: notes.txt committed with one line.

✓ Works

Buy milk

Why: cat prints a file. The edit was never committed, so Git has no copy of it: restore deletes it for good, with no question asked. The second box misspells the name.

The file goes back to modified. Your edit stays.

Ignoring files

Keep passwords, logs and build files out of Git with .gitignore.

What .gitignore does

.gitignore is a text file listing files that Git should act as if it cannot see. Ignored files never show in git status and git add . skips them.

Rule 1List a file in .gitignore and Git stops showing it

Start: a new repo with app.py and a .env file holding a password.

✓ Works
$ git init -q
$ echo 'print(1)' > app.py
$ echo 'PASSWORD=1234' > .env
$ git status --short
?? .env
?? app.py
$ echo '.env' > .gitignore
$ git status --short
?? .gitignore
?? app.py

Why: Before: .env is untracked and would be caught by git add .. After: it disappears from the list. .gitignore itself shows up: commit it, so the rule is saved for everyone.

Rule 2Patterns: *, folders and !

Each line is one pattern.

✓ Works
$ git init -q
$ mkdir build
$ echo x > build/out.bin
$ echo e > error.log
$ echo k > keep.log
$ echo t > todo.txt
$ printf '*.log\n!keep.log\nbuild/\n' > .gitignore
$ cat .gitignore
*.log
!keep.log
build/
$ git status --short
?? .gitignore
?? keep.log
?? todo.txt

Why: *.log: any file ending in .log. !keep.log: except this one. build/: the whole folder. printf writes several lines at once (\n is a new line).

What a branch is

A branch is a separate line of work: commits you make on it do not change other branches. Inside Git it is tiny: just a label pointing at a commit. When you commit, the label of the branch you are on moves forward to the new commit.

Rule 1git branch lists branches

The * marks the branch you are on.

Start: a repo with one commit.

✓ Works
$ git init -q
$ echo Welcome > home.txt
$ git add .
$ git commit -q -m "Add home page"
$ git branch
* main

Start: a repo with one commit.

! Trap: no error, wrong result

$ git add .
$ git commit -q -m "Add home page"
$ git branch menu
$ git branch
* main
  menu

The branch exists, but the * is still on main. A commit now would go on main, not on menu.

Why: git branch menu only puts a new label on the current commit.

Rule 3git switch moves you to a branch

Start: a repo with branches main and menu.

✓ Works
$ git init -q
$ echo Welcome > home.txt
$ git add .

  main
* menu

$ echo Welcome > home.txt
$ git add .

fatal: invalid reference: menus

Merge conflicts

When two branches change the same line, Git asks you to choose. How to read, fix and abort a conflict.

  1. Rule 1Changes to different lines merge on their own
  2. Rule 2Same line changed on both sides: CONFLICT
  3. Rule 3Read the conflict markers
  4. Rule 4Fix it: edit, git add, git commit
  5. Rule 5Check for leftover markers before you commit
  6. Rule 6Changed your mind? git merge --abort

Why conflicts happen

A conflict happens when two branches changed the same lines of the same file, so Git cannot know which version you want. Changes in different files, or in different parts of a file, merge on their own.

Rule 1Changes to different lines merge on their own

Start: a file with three lines; main changes line 1, the other branch changes line 3.

✓ Works
$ git init -q
$ printf 'Dosa 60\nIdli 40\nVada 30\n' > menu.txt
$ git add .
$ git commit -q -m "Menu"
$ git switch -q -c prices
$ sed -i.bak 's/Vada 30/Vada 35/' menu.txt && rm menu.txt.bak
$ git commit -q -am "Vada price"
$ git switch -q main
$ sed -i.bak 's/Dosa 60/Masala dosa 70/' menu.txt && rm menu.txt.bak
$ git commit -q -am "Masala dosa"
$ git merge prices --no-edit
Auto-merging menu.txt
Merge made by the 'ort' strategy.

 1 file changed, 1 insertion(+), 1 deletion(-)
$ cat menu.txt
Masala dosa 70
Idli 40
Vada 35

Why: sed 's/old/new/' replaces text in a file. Both changes are in the result. Auto-merging just means Git combined the file line by line.

Key takeaways

  1. A conflict = both branches changed the same lines.
  2. Between <<<<<<< HEAD and ======= is yours; after it is theirs.
  3. Fix the text, delete the markers, git add, git commit.
  4. git diff --cached --check catches leftover markers.
